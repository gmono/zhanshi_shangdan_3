# 展厅 App 项目约定

本文件记录已确认的资源、界面、同步、错误展示和交付规则，供开发、测试及部署共同遵守。涉及这些规则的修改，必须同时更新本文与对应验证；历史文档与本文不一致时，以本文为准。

## 1. 原始图片与安装目录

正式 Windows 资源目录位于安装目录内，与 `tauronic.exe` 同级：

```text
安装目录/
├── tauronic.exe
├── tools/vips/           # 安装包内置图片处理器
└── 地图资源/
    ├── 左屏/
    │   ├── 1.png
    │   └── 2.png
    ├── 中屏/
    │   ├── 1.png
    │   └── 2.png
    ├── 右屏/
    │   ├── 1.png
    │   └── 2.png
    ├── 图1.jpg
    ├── 图2.jpg           # 后续地图按实际数量放置
    ├── …
    ├── 图10.jpg          # 最多十张，不要求放满
    └── .cache/           # Windows 自动生成的显示缓存
```

- 三个文件夹固定为 `左屏`、`中屏`、`右屏`，从左到右对应主页三栏。
- 每个文件夹必须包含编号 `1`、`2` 的两张图片：`1` 对应分割线左侧图片，`2` 对应右侧图片。编号表示显示位置，不自动解释为年份。
- 对比图支持 `png`、`jpg`、`jpeg`、`tif`、`tiff`、`webp`、`bmp` 扩展名。同一编号只放一个供程序读取的文件，避免多扩展名重复。
- 大图文件名固定为 `图1.jpg` 至 `图10.jpg`；至少需要图1，编号必须连续。缺少图1、对比原图或中间断号时，必须显示缺失文件的具体信息。
- Windows 启动后自动发现实际大图数量并发布资源目录。主页按此目录生成对应按钮；五张显示图1至图5，十张显示图1至图10，不能硬编码成五个按钮或补出不存在的地图。
- 添加、删除或替换原图后重启 Windows 程序。当前不承诺运行中监视文件变化。

## 2. 原图保真与显示缓存

- 用户可直接放入按上述规则命名的原始图片，无须预先缩放、裁剪、改色、配准或制作替代图片。不得为了适配展示覆盖或改写原图。
- 图片尺寸不同时，各自按实际尺寸显示，不生成替代原图来强行统一尺寸。
- Windows 使用 libvips 按需解码并生成 Zoomify 显示瓦片，产物只写入 `.cache/`；显示瓦片是缓存，不能冒充客户原图。
- 缓存依据原文件名、字节数及修改时间验证。同名替换且字节数或修改时间变化时重建，旧的无来源记录缓存不得直接复用。
- iOS 连接 Windows 后获取资源目录、原图尺寸及显示瓦片，不整张解码原始巨图；未连接时显示连接入口。
- 自动测试使用独立生成的测试图，不能修改客户原图。原图只读必须通过处理前后的哈希验证。

## 3. 界面与页面生命周期

- 主页一级分栏固定三等分，不允许拖动；二级分割线初始均在各栏最左边，按比例调整。
- 操作区为底部悬浮半透明胶囊，只在路由容器外保留一份。切换页面通过路由信号更新内容，不能出现两个操作面板同时显示。
- 保留 Ionic 转场。不得通过取消转场、破坏路由或删除其他交互来掩盖黑框和面板重叠问题。
- 地图页离开前，在 `WillLeave` 中通过 ref 设置地图容器 `display:none`；进入前在 `WillEnter` 恢复显示。
- 进入或重新进入单图时，在显示首帧前恢复初始视角；返回主页时恢复一级均分、二级线为零并清空单图操作视角。

## 4. 双端连接与同步顺序

- Windows 是展示端并提供资源及同步服务；iOS 是控制端。iOS 设置只填写 Windows 的局域网 IPv4 地址，支持主动搜索设备。
- 状态同步固定使用 TCP `8787`，资源与通知固定使用 TCP `1421`，设备发现使用 UDP `8789`。同步连接成功不代表资源端口也已连通。
- 连续操作使用 `16ms` 窗口合并并发送最新状态，停止后发送最终状态。窗口设置不等于所有设备和网络条件下均已保证每秒60帧，性能结论必须附实际测试条件。
- 换页与初始状态必须在同一条完整同步消息中发送，先准备和发送状态，再执行本地路由切换，不能依靠延时猜测执行顺序。
- 不同分辨率同步图片内的中心比例与相对放大级数；各端按自己的画布计算显示，不能同步控制端的绝对几何尺寸。单图初始相对视角为中心 `[0.5, 0.5]`、放大 `0`。
- 每条应用层同步消息带递增正整数 `id`；母线广播保留来源 `sourceId` 和房间版本 `revision`。编号在各发送端生命周期内递增，不保证跨服务重启连续。
- 资源通知使用 `ws://Windows地址:1421/events` 主动推送。新连接先收到当前快照，完成状态与资源目录在同一条消息中交付。

## 5. 进度与错误必须明确显示

- Windows 地图准备过程和连接后的 iOS 必须显示当前状态、当前文件、实际完成数量和耗时。处理总数为六张对比图加实际大图数量。
- Rust 处理过程通过闭包直接报告状态，耗时处理放在后台任务；前端收到通知即更新。正常通知连接不通过定时请求 `/progress` 或 `/catalog` 查询状态，也不强制引入 RxJS。
- 原图数量尚未统计完成时，总数可为 `0`。必须接收并显示这种状态下的扫描错误；不显示 `NaN%`、虚假完成比例或无意义的 `0/0` 进度条。
- 缺少资源时显示具体文件夹、文件名或缺少的编号；断号时同时指出缺失文件与发现的后续文件。
- 通知连接10秒未建立，或建立后10秒未收到首条有效状态时，必须显示目标地址、`1421` 端口及具体超时原因，并自动重连。不得无限停留在“正在连接地图处理通知服务”。首条有效状态到达后取消此连接等待超时，正常长时间图片处理不因此被中断。
- JSON、进度或完成目录格式不合法时，必须显示明确的消息校验错误和目标地址；两端版本或资源命名不一致不能被静默忽略。
- 图片处理失败时显示原图路径、图片处理器路径、退出状态、标准错误、标准输出，以及可用的错误记录路径；错误文本必须允许完整查看。
- 通知断线后等待1秒重连；Windows 资源处理失败后每5秒重试。这些是故障恢复定时器，不能代替实时进度通知。
- 明确区分连接失败、等待状态、缺少资源、图片处理失败和完成状态。不能把所有问题都描述为“加载中”或“检查网络”。
- 已显示过地图后再出现资源通知错误，两端也必须在地图上层明确显示错误；不能因为已有缓存目录而隐藏错误。保留地图对象，恢复后继续使用。

## 6. 验证与交付

- GitHub CI 必须从同一提交完成前端检查、Windows 安装后联测、iPad WebKit 与原生连接测试，以及 iOS IPA 构建。
- 验证范围包括十张地图自动发现与首页按钮对应、原图只读、不同尺寸、同名替换缓存、进度和错误通知、页面切换与重新进入复位、两端不同分辨率同步。
- 必须覆盖“服务已返回总数为零的缺图错误”“通知连接无响应”“已连接但没有首条状态”“完成目录不合法”场景，验证用户能看到明确错误，而不只检查后端是否产生错误消息。
- 不同分辨率至少覆盖 `1194×834 → 3840×2160` 和 `1024×1366 → 1920×1080`。本地 iOS 网页模拟与原生 iOS 测试结果分别记录，不能互相冒充。
- Xcode 工程保持 `objectVersion=56`、Xcode 14 兼容格式，未经用户要求不得升级工程格式。
- 签名证书仅在本地使用，不能提交或上传到 GitHub CI。构建与本地签名完成后必须执行 `pnpm artifacts:collect`。
- `out/` 交付同一提交的 `展厅App.ipa`、唯一的 `展厅App-Windows-x64-setup.exe` 和校验清单；不能拿旧包改提交号充当新版本，归档失败必须修复。
- 临时下载、构建辅助资料和测试证据放 `tmp/`，最终成品放 `out/`，二者均不提交 Git。图片、原始巨图、瓦片、预览及生成清单均不提交；`assets/source-images/`、`public/zoomify/` 保持忽略。
